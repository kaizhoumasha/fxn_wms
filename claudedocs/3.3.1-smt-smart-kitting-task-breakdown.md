## 概述 (Overview)

本文档基于 **SRS 3.3.1 SMT 智能装箱协调** 的详细设计，将功能分解为可执行的 Epic 和 User Story，并提供故事点估算、团队速率计算和迭代计划。

### 功能范围

SMT 智能装箱协调系统是一个复杂的多团队协作项目，涉及：

1. **装箱任务呼叫** - 人工模式和系统模式的任务派送
2. **空架补给与验证** - 自动监控和智能补给
3. **栈板拆箱作业** - PDA 扫描和间隔上料控制
4. **视觉识别与 PKG 校验** - 自动扫描和多维度验证
5. **智能分箱算法** - 同类合并、料箱匹配、深度计算
6. **放入确认与绑定** - 机械臂执行和库存同步
7. **满架切出与空架补给** - 容量监控和并行搬运
8. **异常处理** - 三方协同的异常恢复机制

## Epic 1: 装箱任务管理 (Kitting Task Management)

**负责团队**: WMS 团队
**总故事点**: 19 点
**优先级**: P0 (核心功能)
**依赖**: 无 (基础功能)

**Epic 描述**:
实现装箱任务的呼叫、派送、追踪功能，支持人工模式和系统模式两种作业方式。包括 Web 界面的任务呼叫页面、PDA 界面集成、线体路由逻辑、RCS 调度集成和 SignalR 实时状态推送。

**业务价值**:
- 提供灵活的任务派送方式（人工/自动）
- 实现栈板到装箱区的自动化搬运
- 提供实时的任务状态可视化
- 支持多线体智能路由（Line 1/Line 2）

### 用户故事 (User Stories)

#### US-E1-01: Web 界面装箱任务呼叫页面

**作为** 仓库作业员
**我想要** 在 Web 界面上选择待装箱栈板并呼叫装箱任务
**以便** 灵活控制装箱作业的启动时机和优先级

**验收标准** (Acceptance Criteria):
- [ ] GIVEN 用户访问 `/kitting/call` 页面，WHEN 页面加载完成，THEN 显示待装箱栈板列表（状态为 IQC_PASSED 或 EXEMPT）
- [ ] GIVEN 栈板列表，WHEN 用户点击某个栈板，THEN 显示栈板详情（GRN 号、料号、数量、到达时间）
- [ ] GIVEN 用户选择一个或多个栈板（最多 3 个），WHEN 点击"呼叫装箱"按钮，THEN 弹出确认对话框显示预计到达时间和装箱区容量变化
- [ ] GIVEN 用户确认呼叫，WHEN 系统生成 RCS 搬运任务，THEN 任务状态更新为"DISPATCHED"并通过 SignalR 实时推送到前端
- [ ] GIVEN 栈板到达装箱区，WHEN RCS 回调 WMS，THEN 任务状态更新为"ARRIVED"并显示通知
- [ ] GIVEN 装箱区容量已满，WHEN 用户尝试呼叫新任务，THEN 显示警告提示"装箱区已满载，请稍后再试"
- [ ] GIVEN 栈板状态不是 IQC_PASSED 或 EXEMPT，WHEN 用户尝试呼叫，THEN 显示错误提示"栈板状态不允许装箱"
- [ ] GIVEN 用户切换到系统模式，WHEN 系统自动派送任务，THEN 按到达时间顺序自动呼叫栈板

**技术要点**:
- **前端技术**: Blazor Server (C#), SignalR 实时通信
- **UI 组件**: 表格组件（栈板列表）、对话框组件（确认呼叫）、状态指示器（容量监控）
- **数据查询**: Entity Framework Core 查询待装箱栈板（状态筛选、日期筛选）
- **状态管理**: 任务状态枚举（PENDING, DISPATCHED, ARRIVED, IN_PROGRESS, COMPLETED）
- **实时推送**: SignalR Hub 配置（`/hubs/kitting`），客户端订阅任务状态更新
- **测试**: 单元测试（状态转换逻辑）、集成测试（SignalR 推送）、UI 测试（Playwright）

**详细设计参考**: [@docs/design/3.3.1-smt-smart-kitting.md §3.1 装箱任务呼叫](../docs/design/3.3.1-smt-smart-kitting.md#31-装箱任务呼叫-kitting-task-call)

**故事点**: **3**
**估算理由**: 中等复杂度的 Blazor 页面，包含表单、表格、对话框和 SignalR 集成，需要状态管理和实时更新逻辑。

**我想要** 在 PDA 设备上访问装箱任务呼叫功能
**以便** 在装箱区现场灵活操作，无需返回办公室

**验收标准** (Acceptance Criteria):
- [ ] GIVEN PDA 设备通过 WiFi 连接到 WMS，WHEN 访问 `/kitting/call` 页面，THEN 页面自动适配移动端屏幕尺寸
- [ ] GIVEN 移动端页面，WHEN 用户点击栈板，THEN 显示简化的栈板详情（关键信息优先）
- [ ] GIVEN PDA 设备，WHEN 用户呼叫装箱任务，THEN 操作流程与 Web 端一致（确认对话框、状态推送）
- [ ] GIVEN 网络不稳定，WHEN SignalR 连接断开，THEN 显示离线提示并自动重连
- [ ] GIVEN PDA 设备横屏/竖屏切换，WHEN 屏幕方向改变，THEN 页面布局自动调整
- [ ] GIVEN 移动端触摸操作，WHEN 用户滑动列表，THEN 支持下拉刷新和上拉加载更多
- [ ] GIVEN PDA 设备性能限制，WHEN 页面加载，THEN 响应时间 < 2 秒

**技术要点**:
- **响应式设计**: CSS Media Queries, Flexbox 布局
- **移动端优化**: 触摸事件处理、虚拟滚动（大列表性能优化）
- **离线支持**: Service Worker 缓存静态资源、IndexedDB 本地存储
- **网络重连**: SignalR 自动重连机制（`WithAutomaticReconnect()`）
- **性能优化**: Lazy loading, 图片压缩, 代码分割
- **测试**: 移动端浏览器测试（Chrome DevTools）、真机测试（PDA 设备）

**详细设计参考**: [@docs/design/3.3.1-smt-smart-kitting.md §3.1 装箱任务呼叫](../docs/design/3.3.1-smt-smart-kitting.md#31-装箱任务呼叫-kitting-task-call)

**故事点**: **3**
**估算理由**: 移动端适配需要响应式设计和性能优化，SignalR 重连机制增加复杂度。

#### US-E1-03: 线体路由逻辑实现

**作为** 系统
**我想要** 根据料盘尺寸自动分配装箱线体（Line 1 或 Line 2）
**以便** 优化装箱效率和线体利用率

**验收标准** (Acceptance Criteria):
- [ ] GIVEN 栈板包含 7 寸料盘，WHEN 生成装箱任务，THEN 优先分配 Line 1（7 寸专用线）
- [ ] GIVEN Line 1 已满载，WHEN 7 寸料盘任务到达，THEN 自动分配 Line 2（混合尺寸线）
- [ ] GIVEN 栈板包含 13 寸或 15 寸料盘，WHEN 生成装箱任务，THEN 强制分配 Line 2
- [ ] GIVEN 线体容量监控，WHEN 查询线体状态，THEN 返回当前占用率（已占用/总容量）
- [ ] GIVEN 线体路由规则，WHEN 配置参数变更（如 Line 1 容量），THEN 路由逻辑自动适配
- [ ] GIVEN 线体故障，WHEN Line 1 不可用，THEN 所有任务自动路由到 Line 2
- [ ] GIVEN 任务历史记录，WHEN 查询线体分配日志，THEN 显示每个任务的线体分配决策和理由

**技术要点**:
- **路由算法**: 基于料盘尺寸和线体容量的决策树
- **状态查询**: 实时查询 WES 线体占用状态（HTTP API）
- **配置管理**: `appsettings.json` 配置线体容量参数（`Kitting.LineCapacity`）
- **故障转移**: 线体健康检查（Heartbeat），自动切换备用线体
- **日志记录**: 结构化日志（Serilog），记录路由决策过程
- **测试**: 单元测试（路由算法）、集成测试（WES API 调用）、场景测试（故障转移）

**详细设计参考**: [@docs/design/3.3.1-smt-smart-kitting.md §3.1 装箱任务呼叫](../docs/design/3.3.1-smt-smart-kitting.md#31-装箱任务呼叫-kitting-task-call), [@docs/design/3.3.1-smt-smart-kitting.md §3.0.1 双线体系统](../docs/design/3.3.1-smt-smart-kitting.md#301-双线体系统-dual-conveyor-line-system)

**故事点**: **5**
**估算理由**: 复杂的路由决策逻辑，需要实时状态查询、故障转移和配置管理，测试场景多样。

#### US-E1-04: RCS 调度集成与任务追踪

**作为** WMS 系统
**我想要** 调用 RCS API 创建搬运任务并追踪任务状态
**以便** 实现栈板从收货暂存区到装箱区的自动化搬运

**验收标准** (Acceptance Criteria):
- [ ] GIVEN 用户呼叫装箱任务，WHEN WMS 生成搬运任务，THEN 调用 RCS API `POST /api/tasks` 并传递正确参数（task_type, from_location, to_location, pallet_id, priority）
- [ ] GIVEN RCS API 调用成功，WHEN 返回 task_id，THEN WMS 保存 task_id 并更新任务状态为"DISPATCHED"
- [ ] GIVEN RCS API 调用失败，WHEN 返回错误，THEN WMS 重试 3 次（间隔 10 秒），失败后记录日志并通知用户
- [ ] GIVEN RCS 任务执行中，WHEN RCS 回调 WMS `POST /api/wms/tasks/{task_id}/completed`，THEN WMS 更新任务状态为"ARRIVED"
- [ ] GIVEN RCS 任务超时（30 分钟未到达），WHEN 超时检测触发，THEN WMS 发送告警通知并标记任务为"TIMEOUT"
- [ ] GIVEN RCS 任务失败，WHEN RCS 回调失败状态，THEN WMS 记录失败原因并提供人工介入选项
- [ ] GIVEN 任务状态变更，WHEN 状态更新，THEN 通过 SignalR 实时推送到前端界面

**技术要点**:
- **HTTP 客户端**: `HttpClient` 配置（超时、重试策略）
- **重试机制**: Polly 库实现指数退避重试（`RetryPolicy`）
- **回调接口**: ASP.NET Core Web API 接收 RCS 回调（`POST /api/wms/tasks/{task_id}/completed`）
- **超时检测**: 后台服务（`IHostedService`）定时检查任务超时
- **告警通知**: 邮件/短信通知（集成第三方服务）
- **日志记录**: 结构化日志记录 RCS 调用和回调详情
- **测试**: 单元测试（重试逻辑）、集成测试（Mock RCS API）、端到端测试（真实 RCS 环境）

**详细设计参考**: [@docs/design/3.3.1-smt-smart-kitting.md §3.1 装箱任务呼叫](../docs/design/3.3.1-smt-smart-kitting.md#31-装箱任务呼叫-kitting-task-call)

**故事点**: **5**
**估算理由**: 复杂的 HTTP 集成，包含重试机制、回调处理、超时检测和告警通知，测试场景复杂。

#### US-E1-05: SignalR 实时状态推送

**作为** 系统
**我想要** 通过 SignalR 实时推送任务状态变更到前端界面
**以便** 用户无需刷新页面即可看到最新的任务进度

**验收标准** (Acceptance Criteria):
- [ ] GIVEN SignalR Hub 配置完成，WHEN 客户端连接到 `/hubs/kitting`，THEN 连接成功并返回连接 ID
- [ ] GIVEN 任务状态变更（DISPATCHED, ARRIVED, IN_PROGRESS, COMPLETED），WHEN 状态更新，THEN 服务端调用 `Clients.All.SendAsync("TaskStatusChanged", taskData)` 推送消息
- [ ] GIVEN 前端订阅 `TaskStatusChanged` 事件，WHEN 接收到消息，THEN 更新 UI 显示最新状态（无需刷新页面）
- [ ] GIVEN 多个客户端连接，WHEN 任务状态变更，THEN 所有连接的客户端同时接收到更新
- [ ] GIVEN 网络断开，WHEN SignalR 连接中断，THEN 客户端自动重连并重新订阅事件
- [ ] GIVEN 高并发场景（100+ 客户端），WHEN 推送消息，THEN 消息延迟 < 1 秒
- [ ] GIVEN 消息推送失败，WHEN 客户端未接收到消息，THEN 服务端记录日志并重试

**技术要点**:
- **SignalR Hub**: ASP.NET Core SignalR Hub 配置（`MapHub<KittingHub>("/hubs/kitting")`）
- **消息推送**: `IHubContext<KittingHub>` 注入到服务层，调用 `Clients.All.SendAsync()`
- **客户端订阅**: Blazor 组件中使用 `HubConnection` 订阅事件
- **自动重连**: `WithAutomaticReconnect()` 配置重连策略
- **性能优化**: 消息批处理、连接池管理
- **测试**: 单元测试（Hub 方法）、集成测试（多客户端连接）、性能测试（并发推送）

#### US-E3-03: WES 间隔投放控制引擎

- [ ] GIVEN 投放队列非空，WHEN 检查装箱工位状态，THEN 查询 ECS 心跳获取工位可用性
- [ ] GIVEN 工位可用且满足投放间隔，WHEN 计算投放时机，THEN 向 ECS 发送投放指令 `POST /ecs/api/conveyor/release`
- [ ] GIVEN ECS 确认投放，WHEN 返回成功响应，THEN 更新任务状态为 `Released` 并记录时间戳
- [ ] GIVEN ECS 投放超时，WHEN 5 秒未响应，THEN 标记任务为 `Failed` 并发送告警
- [ ] GIVEN 流水线拥堵，WHEN 工位不可用，THEN 延长投放间隔并暂停投放
- [ ] GIVEN 投放间隔配置，WHEN 更新 `release_interval`，THEN 投放逻辑自动适配

**技术要点**:
- **技术栈**: Python 3.11+, FastAPI, Redis (队列), asyncio
- **投放算法**:
  ```python
  async def interval_release_controller():
      while True:
          if queue.is_empty():
              await asyncio.sleep(1)
              continue

          task = queue.peek()
          if not is_workstation_ready():
              await asyncio.sleep(5)
              continue

          if time.time() - last_release_time < INTERVAL:
              await asyncio.sleep(1)
              continue

          await release_to_ecs(task)
          queue.dequeue()
          last_release_time = time.time()
  ```
- **Redis 数据结构**:
  - `unpacking_queue`: List (FIFO 队列)
  - `task:{taskId}`: Hash (任务状态)
  - `workstation:{lineId}:status`: String (工位状态)
- **ECS 集成**: HTTP POST with retry (3 attempts, 5s timeout)
- **监控指标**: 投放成功率、平均投放间隔、队列长度

**详细设计参考**: [@docs/design/3.3.1-smt-smart-kitting.md §3.3.3 WES 间隔投放控制](../docs/design/3.3.1-smt-smart-kitting.md#333-wes-间隔投放控制)

**故事点**: **8**
**估算理由**: 复杂的异步控制逻辑，包含队列管理、状态监控、动态调整，测试场景复杂。

#### US-E5-01: 同类合并算法

**作为** WES 系统
**我想要** 将相同 GRN 的物料合并到同一箱号
**以便** 提高货架利用率和拣选效率

**验收标准** (Acceptance Criteria):
- [ ] GIVEN 物料校验通过，WHEN 触发分箱算法，THEN 查询货架中是否存在相同 GRN 的箱号
- [ ] GIVEN 存在相同 GRN 箱号，WHEN 检查箱号容量，THEN 计算剩余空间是否足够放入新物料
- [ ] GIVEN 剩余空间足够，WHEN 选择箱号，THEN 优先选择已有物料的箱号（同类合并）
- [ ] GIVEN 剩余空间不足，WHEN 无法合并，THEN 选择新的空箱号
- [ ] GIVEN 多个相同 GRN 箱号，WHEN 选择箱号，THEN 优先选择剩余空间最小的箱号（最优填充）
- [ ] GIVEN 货架无相同 GRN 箱号，WHEN 分配新箱号，THEN 选择空箱号并标记 GRN
- [ ] GIVEN 分箱决策完成，WHEN 返回结果，THEN 包含 rack_id, bin_id, slot_id, expected_height

**技术要点**:
- **技术栈**: Python 3.11+, Redis (货架状态缓存)
- **算法逻辑**:
  ```python
  def find_best_bin(pkg, racks):
      # 1. 查找相同 GRN 的箱号
      same_grn_bins = [bin for rack in racks for bin in rack.bins
                       if bin.grn_id == pkg.grn_id and bin.status == 'IN_USE']

      # 2. 过滤容量足够的箱号
      available_bins = [bin for bin in same_grn_bins
                        if bin.remaining_height >= pkg.thickness]

      # 3. 选择剩余空间最小的箱号（最优填充）
      if available_bins:
          return min(available_bins, key=lambda b: b.remaining_height)

      # 4. 无相同 GRN 箱号，选择空箱号
      empty_bins = [bin for rack in racks for bin in rack.bins
                    if bin.status == 'EMPTY']
      if empty_bins:
          return empty_bins[0]

      return None  # 无可用箱号
  ```
- **Redis 数据结构**:
  - `rack:{rack_id}:bins`: Hash (箱号状态)
  - `bin:{bin_id}:grn_id`: String (GRN 绑定)
  - `bin:{bin_id}:remaining_height`: Float (剩余高度)
- **性能优化**: 缓存货架状态，避免频繁查询数据库
- **测试**: 单元测试（算法逻辑）、集成测试（Redis 状态查询）、场景测试（边界条件）

**详细设计参考**: [@docs/design/3.3.1-smt-smart-kitting.md §3.5.1 同类合并算法](../docs/design/3.3.1-smt-smart-kitting.md#351-同类合并算法)

**故事点**: **5**
**估算理由**: 复杂的算法逻辑，包含多条件筛选、最优选择、状态管理，测试场景多样。

              if await retry_grasp(pkg_code):
                  return Success()
          # 抓取失败，人工介入

### D. 验收标准模板 (Acceptance Criteria Template)

**标准格式**: GIVEN-WHEN-THEN

```
- [ ] GIVEN [前置条件], WHEN [操作], THEN [预期结果]
```

**示例**:
```
- [ ] GIVEN 用户已登录, WHEN 点击"呼叫装箱", THEN 显示线体选择界面
- [ ] GIVEN 选择线体 L1, WHEN 提交呼叫, THEN 创建装箱任务并返回任务 ID
- [ ] GIVEN 任务创建成功, WHEN RCS 接收任务, THEN 任务状态更新为"已调度"
```

**验收检查清单**:
- [ ] 功能完整性: 所有验收标准通过
- [ ] 代码质量: 通过 Code Review
- [ ] 单元测试: 覆盖率 ≥ 80%
- [ ] 集成测试: 关键路径测试通过
- [ ] 性能测试: 响应时间 < 2s (API)，< 5s (批处理)
- [ ] 安全测试: 无 SQL 注入、XSS 等漏洞
- [ ] 文档更新: API 文档、用户手册更新

### E. 团队协作指南 (Team Collaboration Guide)

**日常站会** (Daily Standup):
- 时间: 每天上午 9:30，15 分钟
- 内容: 昨天完成、今天计划、遇到的阻碍

**Sprint 计划会** (Sprint Planning):
- 时间: 每个 Sprint 第一天，2 小时
- 内容: 选择 User Story，分解任务，估算工作量

**Sprint 评审会** (Sprint Review):
- 时间: 每个 Sprint 最后一天，1 小时
- 内容: 演示完成功能，收集反馈

**Sprint 回顾会** (Sprint Retrospective):
- 时间: 每个 Sprint 最后一天，1 小时
- 内容: 总结经验教训，改进流程

**代码 Review 规范**:
- 所有代码必须经过 Review 才能合并
- Review 重点: 功能正确性、代码质量、安全性
- Review 时间: 24 小时内完成

**集成测试节点**:
- Sprint 2 结束: 装箱任务管理 + 空架生命周期
- Sprint 4 结束: 栈板拆箱 + 视觉识别
- Sprint 6 结束: 智能分箱算法
- Sprint 8 结束: 放入执行 + 库存绑定
- Sprint 10 结束: 全流程集成测试
