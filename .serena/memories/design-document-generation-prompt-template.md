# 设计文档生成 PROMPT 模板

## 使用方法

当用户提供：
1. 规格文档路径（如 `@docs/SRS.md`）
2. 具体需求章节（如 `3.2.2 IQC 动态路由与复判`）

按以下 PROMPT 生成设计文档。

---

## PROMPT 模板

```
请基于以下规格文档和需求章节，生成详细设计文档：

**规格文档**: [用户指定的 SRS 章节]
**需求章节**: [用户指定的具体章节，如 3.2.2]
**参考文档**: @docs/user_requirement.md（用于审计和验证）

**设计文档要求**:

### 1. 文档结构（按以下顺序）

#### 1.1 技术栈说明 (Technology Stack)
- WMS 技术架构（Blazor Server 前后端不分离）
- WES 技术架构（Python/Java）
- 集成架构图（Mermaid 格式）
- Blazor 代码示例（如有 WMS-WES 交互）
- 配置说明（appsettings.json）
- 部署架构图（Mermaid 格式）

#### 1.2 范围与依据 (Scope & Traceability)
- 基于 SRS 的具体章节引用
- 过程参考文档
- 需求参考文档
- 范围说明（明确 WMS/WES 职责边界）

#### 1.3 角色与归属 (Actors & Ownership)
表格格式，包含：
- 子功能名称
- 归属系统（WMS/WES/RCS/硬件供应商）
- 详细说明

**关键原则**:
- 明确 WMS 和 WES 的职责边界
- 当前阶段 WMS 可能独立负责某些功能，WES 不参与
- 打印机、RCS 调度等由谁负责要明确

#### 1.4 前提与配置 (Preconditions & Config)
- 主数据维护方
- 地码配置
- 编码规则
- 幂等键设计
- 网络/权限要求
- 设备接入规范

#### 1.5 子功能流程设计 (Sub-function Flows)
按业务流程顺序，每个子功能包含：
- 流程步骤（编号清晰）
- 参与方（WMS/WES/RCS/人工/设备）
- 数据流向
- 校验逻辑
- 异常处理

#### 1.6 典型时序 (Mermaid Sequence)
```mermaid
sequenceDiagram
    participant 作业员
    participant WMS
    participant SAP
    participant WES
    participant 设备
    participant RCS
    
    [详细时序图]
```

#### 1.7 工业操作对齐要点 (Industrial Ops Alignment)
- 顺序控制
- 区域一致性
- 安全约束
- 幂等与恢复
- 边界遵循

#### 1.8 数据要点 (Data Notes)
- 关键数据对象
- 数据归属（WMS/WES）
- 数据结构示例

#### 1.9 功能页面设计 (Functional Page Design)

##### WMS Web 页面
每个页面包含：
- 路径
- 角色
- 页面元素（表单、按钮、显示区域）
- 交互逻辑（流程图或步骤）
- 关键特性

##### WMS PDA 界面
每个界面包含：
- 界面类型
- 角色
- 界面流程（步骤化）
- 界面特性（大字体、扫描枪、快捷键等）

#### 1.10 特殊机制设计（如需要）
根据业务需求，可能包含：
- 双向校验机制
- 临时编号机制
- 异常处理机制
- 状态转换图
- 数据一致性保证

每个机制包含：
- 设计原则
- 数据库模型（SQL）
- 业务逻辑（伪代码）
- UI 交互设计
- 异常处理流程

### 2. 架构边界原则（关键！）

**在设计过程中，必须遵循以下原则**:

1. **职责明确**: 
   - 明确每个功能由 WMS 还是 WES 负责
   - 不要假设 WES 参与所有自动化流程
   - 当前阶段可能 WMS 独立完成某些功能

2. **API 设计**:
   - 只设计真正需要的 WMS-WES 集成 API
   - 不要设计 WMS 内部 API
   - 不要设计 WES 南向 API（设备接口）
   - 不要设计 WES 内部 API

3. **设备管理**:
   - 明确打印机由谁管理（WMS 直接 TCP？还是通过 WES？）
   - 明确 RCS 由谁调度（WMS 直接？还是通过 WES？）
   - 明确 PDA 连接到哪个系统

4. **数据归属**:
   - 明确哪些数据由 WMS 持有
   - 明确哪些数据由 WES 持有
   - 避免数据重复维护

5. **简化优先**:
   - 使用第一性原理思考
   - 避免过度设计
   - 能自动化的就自动化
   - 能简化的就简化

### 3. 审计要求

**在完成设计后，必须进行以下审计**:

#### 3.1 与 user_requirement.md 的对照审计

对照 user_requirement.md 中对应章节（如"码头到收货暂存区"），检查：

1. **功能完整性**:
   - 列出 user_requirement.md 中的所有步骤
   - 逐一确认设计文档是否覆盖
   - 标注缺失的功能

2. **流程一致性**:
   - 对比业务流程顺序
   - 确认参与方一致（WMS/RCS/人工等）
   - 确认数据流向一致

3. **硬件使用一致性**:
   - 对比硬件清单
   - 确认 PDA、打印机、电脑的使用场景一致

4. **输出审计报告**:
```markdown
## 审计报告

### 覆盖的需求
- [需求编号] [需求描述] ✓

### 缺失的需求
- [需求编号] [需求描述] ✗ [原因]

### 不一致的地方
- [需求编号] [差异描述] [建议]

### 新增的设计
- [设计内容] [理由]
```

#### 3.2 内部一致性审计

检查设计文档内部：
1. 角色与归属表 vs 子功能流程设计（职责是否一致）
2. 时序图 vs 子功能流程（流程是否一致）
3. 功能页面设计 vs 子功能流程（UI 是否支持流程）
4. 数据要点 vs 数据库模型（数据结构是否一致）

### 4. 输出格式

**文件名**: `[章节号]-[功能名称].md`
例如: `3.2.2-iqc-routing-review.md`

**语言**: 中文为主，技术术语保留英文，格式为"中文 (English)"

**Markdown 格式**:
- 使用标准 Markdown 语法
- 代码块使用 ```语言标识
- 表格使用标准 Markdown 表格
- Mermaid 图使用 ```mermaid

### 5. 迭代改进机制

如果用户指出架构边界错误（如"WES 不参与此阶段"），应该：
1. 立即更新相关章节
2. 移除不必要的 API 设计
3. 更新角色与归属表
4. 更新时序图
5. 更新代码示例
6. 确保文档内部一致性

**不要争辩，直接按用户指示修正**。

## 关键经验教训（从 3.2.1 设计中学到的）

### 架构边界教训

1. **不要假设 WES 参与所有流程**
   - 3.2.1 最终确认：WMS 全权负责码头收货绑定，WES 不参与
   - 教训：先明确职责边界，再设计流程

2. **不要假设需要 WMS-WES API**
   - 3.2.1 最终确认：无需任何 WMS-WES API
   - 教训：只设计真正需要的集成接口

3. **不要假设 WES 管理打印机**
   - 3.2.1 最终确认：WMS 通过 TCP 端口 9100 直接管理打印机
   - 教训：明确设备管理归属

4. **不要假设 WES 调度 RCS**
   - 3.2.1 最终确认：WMS 直接调度 RCS
   - 教训：明确硬件调度归属

### 业务逻辑教训

1. **箱数 ≠ 栈板数**
   - 不能从箱数自动推导栈板数
   - 需要人工根据实际情况确定

2. **一个箱子不可能需要多个栈板**
   - 但一个栈板可以装多个箱子

3. **使用第一性原理简化设计**
   - 去除不必要的确认页面
   - 自动化能自动化的步骤
   - 后台执行不阻塞用户

### 设计流程教训

1. **先读 SRS，再读 user_requirement**
2. **先明确架构边界，再设计流程**
3. **先设计核心流程，再设计 UI**
4. **先设计正常流程，再设计异常处理**
5. **持续审计，确保一致性**
