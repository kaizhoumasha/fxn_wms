# 设计文档生成器 (Design Document Generator)

基于 SRS 规格文档和具体需求章节，生成详细设计文档。

## 使用方法

```
/design <章节号> <章节名称>
```

**示例**:
```
/design 3.2.2 IQC 动态路由与复判
```

---

## 工具与思考模式

**启用模式**: `--ultrathink` (最大深度分析)

**可用工具**:
- **Sequential Thinking**: 复杂推理、架构分析、假设验证
- **Serena Tools**: 代码探索、符号操作、项目记忆管理

## 执行步骤

### 0. 物理布局调研（针对硬件密集型功能）

**适用场景**: 涉及硬件设备、传感器、机械臂、流水线等物理设备的功能

**调研内容**:
- 询问用户物理硬件布局（流水线、工位、传感器位置）
- 了解硬件自主控制循环（如：传感器触发 → 硬件动作）
- 明确硬件职责边界（ECS 自主控制 vs ECS → WES 上报）
- 确认物理约束（如：线体容量、工位数量、尺寸限制）

**输出**: 在设计文档中创建 §3.0 物理布局与硬件配置章节

### 3. 架构边界原则（关键！）

**在设计过程中，必须遵循以下原则**:

1. **职责明确**:
   - 明确每个功能由 WMS 还是 WES 负责
   - 不要假设 WES 参与所有自动化流程
   - 当前阶段可能 WMS 独立完成某些功能

2. **API 设计**:
   - 只设计真正需要的 WMS-WES 集成 API
   - 不要设计 WMS 内部 API
   - 不要设计 WES 南向 API（设备接口）
   - 不要设计 WES 内部 API

3. **设备管理**:
   - 明确打印机由谁管理（WMS 直接 TCP？还是通过 WES？）
   - 明确 RCS 由谁调度（WMS 直接？还是通过 WES？）
   - 明确 PDA 连接到哪个系统

4. **数据归属**:
   - 明确哪些数据由 WMS 持有
   - 明确哪些数据由 WES 持有
   - 避免数据重复维护

5. **简化优先**:
   - 使用第一性原理思考
   - 避免过度设计
   - 能自动化的就自动化
   - 能简化的就简化

6. **外部硬件供应商边界**:
   - 硬件供应商（ECS）是外部团队，不描述其内部实现细节
   - 只定义能力需求和接口规范（WHAT），不描述实现方法（HOW）
   - 所有硬件交互必须遵循 `docs/third_party_integration_whitepaper.md`
   - 使用"需要提供...能力"而非"使用...技术实现"
   - 物理布局和约束可以描述（影响业务逻辑），但控制逻辑不描述

7. **WMS/WES 职责分工**:
   - **WMS 负责人工兜底**：提供完整的人工操作流程，确保业务连续性
   - **WES 负责自动化增强**：在 WMS 基础上增加自动化能力，提升效率
   - WMS 是业务的安全网，WES 是效率的加速器
   - 自动化失败时，必须能回退到 WMS 的人工流程
   - 设计时优先保证 WMS 人工流程完整，再考虑 WES 自动化增强

- **自动化降级**: 自动化失败时，切换到人工模式

## 关键经验教训

### 架构边界教训

1. **不要假设 WES 参与所有流程**
   - 教训：先明确职责边界，再设计流程

2. **不要假设需要 WMS-WES API**
   - 教训：只设计真正需要的集成接口

3. **不要假设 WES 管理打印机**
   - 教训：明确设备管理归属

4. **不要假设 WES 调度 RCS**
   - 教训：明确硬件调度归属

### 工作流模式教训

1. **不要假设自动推送 (Push) 总是最优**
   - 教训：考虑现场容量限制和人员控制需求，拉动式可能比推动式更有效

2. **不要假设自动完成总是可靠**
   - 教训：关键节点需要人工确认，但要配合兜底机制（定时轮询）防止遗忘

3. **提醒机制 + 兜底机制 = 可靠性**
   - 教训：设计要考虑人的遗忘，用技术手段保证流程不中断

### 业务实体关系教训

1. **一个栈板可能包含多个 GRN**
   - 教训：不要假设一对一关系，要考虑一对多、多对多的复杂关系

2. **一个 GRN 可能分布在多个栈板上**
   - 教训：业务实体的物理分布可能很复杂，要考虑批量操作

3. **管理对象选择：业务逻辑 > 物理操作**
   - 教训：选择管理对象时，优先考虑业务逻辑而非物理操作便利性

### 物理布局优先原则

1. **先调研物理布局，再设计功能流程**
   - 教训：物理硬件约束决定了业务流程的可行性，必须优先调研

2. **物理布局应作为 §3.0 独立章节**
   - 教训：物理布局是后续功能流程的基础，应该最先设计和验证

3. **物理约束驱动路由逻辑**
   - 教训：物理约束不是实现细节，而是业务逻辑的一部分

### 业务实体 vs 物理实体

1. **区分业务实体和物理实体**
   - 教训：业务实体 (GRN) 和物理实体 (Pallet) 是不同的，操作要匹配物理实体

2. **UI 应反映实际操作对象**
   - 教训：UI 选择的对象应该与后续物理操作的对象一致

3. **业务实体可以关联到物理实体**
   - 教训：不要混淆两种实体，而是建立清晰的关联关系

### 硬件自主控制边界

1. **ECS 应自主处理本地控制循环**
   - 教训：硬件的本地控制循环应由 ECS 自主完成，无需 WES 微管理

2. **仅上报业务相关的最终结果**
   - 教训：减少不必要的网络交互，WES 只关心业务相关的结果

3. **移除不必要的 WES → ECS 接口**
   - 教训：如果 ECS 能自主完成，就不需要 WES 调用接口

### 外部团队协作原则

1. **不要描述外部团队的实现细节，只定义需求和接口**
   - 教训：外部团队的设计文档应聚焦 WHAT（需要什么能力），而非 HOW（如何实现）

2. **区分内部控制循环和跨系统交互**
   - 教训：硬件的本地控制循环应由硬件团队自主完成，只上报业务相关的最终结果

3. **接口设计要聚焦协调所需，不要微管理**
   - 教训：接口应该是高层次的协调指令，不是低层次的控制命令

4. **遵循第三方集成白皮书**
   - 所有 WES-ECS 交互必须遵循 `docs/third_party_integration_whitepaper.md`
   - 使用白皮书定义的标准接口：
     - Vendor Implementation: Receive Command, Health Check, Cancel Command
     - WES Callback: Report Result, Event Push
   - 引用白皮书章节而非重新定义接口

5. **描述方式对比**
   - ✅ 正确：
     - "ECS 需要提供料盘到位检测能力"
     - "ECS 通过 Event Push 接口（whitepaper §3.2.2）上报扫描结果"
     - "WES 通过 Receive Command 接口（whitepaper §3.1.1）下发抓取指令"
   - ❌ 错误：
     - "ECS 使用光电传感器检测料盘到位"
     - "ECS 串杆步进控制逻辑为..."
     - "ECS 内部使用 PLC 控制..."

6. **物理约束 vs 实现细节**
   - ✅ 可以描述：物理布局（如"8工位串杆系统"）、容量限制、尺寸约束
   - ❌ 不要描述：传感器类型、PLC 逻辑、控制算法、内部状态机

### 数据可用性验证原则

1. **不要假设数据存在，要验证数据来源**
   - 教训：设计计算逻辑前，先验证所需数据是否在该时间点可用

2. **数据可用性验证清单**
   - 问题 1：这个数据在哪个系统？（WMS/WES/SAP/QMS）
   - 问题 2：这个数据在什么时候可用？（收货时/扫描后/检验后）
   - 问题 3：这个数据的来源是什么？（人工录入/系统计算/外部接口）
   - 问题 4：如果数据不可用，有替代方案吗？

3. **避免"便利性假设"**
   - 教训：不要因为某个设计"看起来更好"就假设数据存在，要基于数据现实设计

### 任务模型设计原则

1. **选择正确的任务粒度**
   - 教训：任务粒度应该基于业务自然单元，不是技术便利性

2. **任务粒度选择清单**
   - 问题 1：什么是业务上的自然工作单元？（栈板/箱/料盘/批次）
   - 问题 2：什么必须作为原子操作完成？（不可中断的最小单元）
   - 问题 3：任务状态如何跟踪？（粒度越细，状态管理越复杂）
   - 问题 4：任务失败如何恢复？（粒度影响恢复策略）

3. **避免过度优化的任务模型**
   - 教训：简单的任务模型通常比复杂的优化模型更可靠、更易维护

### 任务完整性原则

1. **定义清晰的任务边界**
   - 教训：任务边界要包含所有相关工作，包括异常处理

2. **任务完整性检查清单**
   - 问题 1：任务的前置条件是什么？（开始前必须满足的条件）
   - 问题 2：任务的完成标准是什么？（什么情况下算完成）
   - 问题 3：任务的异常情况如何处理？（NG 料盘、设备故障等）
   - 问题 4：任务之间的依赖关系是什么？（必须完成 A 才能开始 B）

3. **避免"乐观路径"设计**
   - 教训：任务完整性设计要考虑异常路径，不能只考虑正常路径

### 设计流程教训

1. **先调研物理布局，再设计功能流程**
2. **先区分业务实体和物理实体，再设计操作流程**
3. **先明确硬件自主控制边界，再设计系统交互**
4. **先验证物理逻辑，再完善业务逻辑**
5. **先明确团队性质（内部/外部），再选择设计方法**
6. **先验证数据可用性，再设计计算逻辑**
7. **先验证物理约束，再编码业务规则**
8. **先确定任务粒度，再设计任务流程**
9. **先定义任务完整性，再设计状态转换**
10. **接受多轮迭代，每轮聚焦不同层面**
11. **持续接受用户反馈，快速迭代设计**
