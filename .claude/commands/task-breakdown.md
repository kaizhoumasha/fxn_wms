# 任务分解生成器 (Task Breakdown Generator)

基于详细设计文档生成可评估的任务分解文档，包含史诗故事、用户故事、故事点估算、团队速率计算和迭代计划。

## 使用方法

```
/task-breakdown <设计文档路径> [选项]
```

**示例**:
```
/task-breakdown docs/design/3.2.1-dock-receiving-binding.md
/task-breakdown docs/design/3.2.1-dock-receiving-binding.md --team-size 2 --productivity 2
```

---

## 工具与思考模式 (Tools & Thinking Mode)

**启用模式**: `--ultrathink` (最大深度分析，~32K tokens)

**可用工具**:
- **Sequential Thinking** (`mcp__sequential-thinking__sequentialthinking`): 用于系统性分析、任务分解、估算验证
- **Serena Tools** (`mcp__serena__*`): 用于文档探索、模式搜索、引用管理
  - `search_for_pattern`, `list_dir`, `find_file` - 文档定位
  - `read_file` - 读取设计文档和需求文档
  - `write_memory`, `read_memory` - 任务分解结果持久化

**使用场景**:
- 设计文档分析 → Sequential Thinking
- Epic/User Story 分解 → Sequential Thinking
- 故事点估算 → Sequential Thinking
- 团队速率计算 → Sequential Thinking
- 文档引用建立 → Serena search tools

## 命令参数

### 必需参数
- `<设计文档路径>`: 详细设计文档的路径（相对或绝对路径）

### 可选参数
- `--team-size <数量>`: 团队人数（默认: 2）
- `--productivity <人时/故事点>`: 开发生产率（默认: 2 人时/故事点）
- `--sprint-weeks <周数>`: 迭代周期（默认: 2 周）
- `--effective-rate <百分比>`: 有效工时占比（默认: 65%）
- `--output <路径>`: 输出文件路径（默认: `claudedocs/<章节>-task-breakdown.md`）
- `--optimize`: 启用效率优化建议

## 生成流程

### 步骤 1: 读取和分析设计文档

1. **读取设计文档**
   - 使用 `read_file` 读取指定的设计文档
   - 识别设计文档对应的 SRS 章节
   - 提取关键功能模块和子功能流程

2. **读取相关需求文档**
   - 读取 `@docs/SRS.md` 中对应章节
   - 读取 `@docs/user_requirement.md` 中相关需求
   - 读取 `@docs/mock_data.md` 作为数据验证参考

3. **分析设计内容**
   - 识别所有子功能流程（Sub-function Flows）
   - 提取角色与归属（Actors & Ownership）
   - 识别团队分工（WMS/WES/ECS/协同）
   - 提取功能页面设计（Functional Page Design）
   - 识别数据模型和接口定义

### 步骤 2: Epic 分解

1. **识别 Epic**
   - 根据设计文档的主要功能模块划分 Epic
   - 每个 Epic 对应一个完整的业务能力
   - 确定 Epic 的负责团队（WMS/WES/ECS）
   - 设置 Epic 优先级（P0/P1/P2）

2. **Epic 描述**
   - 为每个 Epic 编写清晰的描述
   - 说明 Epic 的业务价值
   - 标注 Epic 之间的依赖关系

### 步骤 3: User Story 分解

1. **从 Epic 分解 User Story**
   - 每个 Epic 分解为 3-8 个 User Story
   - 使用标准格式：
     ```
     作为 <角色>
     我想要 <功能>
     以便 <业务价值>
     ```

2. **编写验收标准**
   - 为每个 User Story 编写 5-10 条验收标准
   - 使用可测试的、明确的标准
   - 包含正常流程和异常处理

3. **技术要点**
   - 列出实现该 User Story 的关键技术点
   - 包含技术栈、框架、库、集成点
   - 标注技术难点和风险

4. **设计文档引用**
   - 为每个 User Story 添加设计文档引用
   - 格式：`**详细设计参考: [@docs/design/X.X.X §Y.Y 章节名称](路径#锚点)**`
   - 支持多个引用（用逗号分隔）

### 步骤 4: 故事点估算

1. **使用 Fibonacci 序列**
   - 1: 极简单（单一 CRUD，无业务逻辑）
   - 2: 简单（基础表单，简单验证）
   - 3: 中等（多步骤流程，中等验证）
   - 5: 复杂（复杂业务规则，多集成点）
   - 8: 很复杂（复杂工作流，状态机）
   - 13: 史诗级（应拆分为多个故事）
   - 21: 过大（必须拆分）

2. **估算考虑因素**
   - 技术复杂度
   - 业务逻辑复杂度
   - 集成点数量
   - 测试复杂度
   - 不确定性

3. **估算理由**
   - 为每个故事点估算提供简短理由
   - 说明主要复杂度来源

### 步骤 5: 团队速率计算

1. **基础产能计算**
   ```
   可用工时 = 团队人数 × 迭代天数 × 每天工时
   有效工时 = 可用工时 × 有效工时占比
   综合工时 = 开发工时 + 测试工时 + 集成工时
   团队速率 = 有效工时 ÷ 综合工时系数
   ```

2. **参数说明**
   - **团队人数**: 实际开发人员数量
   - **生产率**: 纯开发时间（人时/故事点）
   - **有效工时占比**: 考虑会议、代码审查等（建议 65-70%）
   - **综合工时系数**: 开发 + 测试 + 集成（建议 3.0-3.5）

3. **效率优化建议**（如果启用 `--optimize`）
   - 提升有效工时占比的措施
   - 降低综合工时系数的措施
   - 自动化测试和 CI/CD 建议
   - 代码复用和组件库建议

### 步骤 6: 迭代计划

1. **Sprint 分配**
   - 根据团队速率分配故事点到各个 Sprint
   - 考虑 Epic 依赖关系
   - 平衡各 Sprint 的工作量

2. **Sprint 详细计划**
   - 列出每个 Sprint 包含的 User Story
   - 标注故事点和工时估算
   - 明确依赖关系
   - 如果是多人团队，分配负责人（Dev1/Dev2）

3. **并行开发策略**
   - 识别可并行开发的任务
   - 建议前后端分离策略
   - 标注需要结对编程的复杂模块

4. **关键里程碑**
   - 为每个 Sprint 定义 3-5 个关键里程碑
   - 使用 Day X 格式标注时间点
   - 包含集成测试和验收节点

5. **风险与缓解**
   - 识别高风险、中风险项
   - 提供具体的缓解措施

### 步骤 7: 团队协作时间表

1. **周次分配**
   - 按周次列出各团队工作内容
   - 标注协作事项（SAP 集成、RCS 集成等）
   - 计算工时投入
   - 说明并行策略

2. **关键协作点**
   - 列出跨团队协作的关键时间点
   - 标注主导方和支持方
   - 包含环境配置、联调、测试等

3. **效率提升关键**
   - Sprint 0 准备工作
   - 自动化优先策略
   - 并行开发策略
   - 代码复用策略

4. **总工时和总工期**
   - 计算 P0 功能总工时
   - 计算 P1 可选功能工时
   - 给出总工期估算

### 步骤 8: 附录内容

1. **估算参考**
   - Fibonacci 故事点参考表
   - 团队速率参考
   - 预估迭代计划

2. **依赖关系图**
   - 使用文本图表展示 Epic 依赖关系
   - 标注关键路径

3. **风险与缓解措施**
   - 高风险项列表
   - 中风险项列表
   - 具体缓解措施

4. **验收标准总览**
   - 功能完整性标准
   - 性能要求
   - 可靠性要求
   - 数据质量要求

## 示例用法


生成任务分解文档到指定路径

## 注意事项

1. **设计文档必须完整**: 确保设计文档包含所有必要章节（子功能流程、角色归属、功能页面设计等）
2. **团队分工明确**: 设计文档中必须明确标注各功能的负责团队
3. **故事点估算一致性**: 使用统一的估算标准，确保团队理解一致
4. **依赖关系准确**: 正确识别 Epic 和 User Story 之间的依赖关系
5. **引用链接有效**: 确保设计文档引用的锚点正确，链接可点击
6. **工时计算合理**: 考虑实际团队情况，不要过于乐观或悲观
7. **迭代计划可行**: Sprint 分配要考虑团队实际产能和依赖关系
