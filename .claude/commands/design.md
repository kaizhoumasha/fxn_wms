# 设计文档生成器 (Design Document Generator)

基于 SRS 规格文档和具体需求章节，生成详细设计文档。

## 使用方法

```
/design <章节号> <章节名称>
```

**示例**:
```
/design 3.2.2 IQC 动态路由与复判
```

---

## 执行步骤

请按以下步骤生成设计文档：

### 1. 读取输入文档

- 读取 `@docs/SRS.md` 中用户指定的章节
- 读取 `@docs/user_requirement.md` 中的相关需求（用于理解业务背景）
- 读取 `@docs/design/3.2.1-dock-receiving-binding.md` 作为格式参考

### 2. 生成设计文档（分阶段写入）

**重要**: 为避免 TOKEN 超长导致文件创建失败，设计文档必须分阶段生成和写入。

#### 阶段 1: 创建文档框架（Write 工具）

生成并写入文档头部和基础章节：

**包含内容**:
- 文档标题
- 技术栈说明 (Technology Stack)
  - WMS 技术架构（Blazor Server 前后端不分离）
  - WES 技术架构（Python/Java）
  - 集成架构图（Mermaid 格式）
  - Blazor 代码示例（如有 WMS-WES 交互）
  - 配置说明（appsettings.json）
  - 部署架构图（Mermaid 格式）
- 范围与依据 (Scope & Traceability)
- 角色与归属 (Actors & Ownership)
- 前提与配置 (Preconditions & Config)

**操作**: 使用 Write 工具创建文件 `docs/design/[章节号]-[功能名称].md`

#### 阶段 2: 添加核心流程设计（Edit 工具追加）

生成并追加核心业务流程：

**包含内容**:
- 子功能流程设计 (Sub-function Flows)
  - 按业务流程顺序，每个子功能包含：
    - 流程步骤（编号清晰）
    - 参与方（WMS/WES/RCS/人工/设备）
    - 数据流向
    - 校验逻辑
    - 异常处理

**操作**: 使用 Edit 工具在文件末尾追加内容

**注意**: 如果子功能流程过多（>5个），可以分批追加

#### 阶段 3: 添加时序图和对齐要点（Edit 工具追加）

生成并追加时序图和工业操作要点：

**包含内容**:
- 典型时序 (Mermaid Sequence)
  ```mermaid
  sequenceDiagram
      participant 作业员
      participant WMS
      participant SAP
      participant WES
      participant 设备
      participant RCS

      [详细时序图]
  ```
- 工业操作对齐要点 (Industrial Ops Alignment)
  - 顺序控制
  - 区域一致性
  - 安全约束
  - 幂等与恢复
  - 边界遵循
- 数据要点 (Data Notes)
  - 关键数据对象
  - 数据归属（WMS/WES）
  - 数据结构示例

**操作**: 使用 Edit 工具在文件末尾追加内容

#### 阶段 4: 添加功能页面设计（Edit 工具追加）

生成并追加界面设计：

**包含内容**:
- 功能页面设计 (Functional Page Design)
  - WMS Web 页面（每个页面包含路径、角色、页面元素、交互逻辑、关键特性）
  - WMS PDA 界面（每个界面包含界面类型、角色、界面流程、界面特性）

**操作**: 使用 Edit 工具在文件末尾追加内容

**注意**: 如果页面/界面过多（>5个），可以分批追加

#### 阶段 5: 添加特殊机制和总结（Edit 工具追加）

生成并追加特殊机制设计和文档总结：

**包含内容**:
- 特殊机制设计（如需要）
  - 双向校验机制、临时编号机制、异常处理机制、状态转换图、数据一致性保证
  - 每个机制包含：设计原则、数据库模型、业务逻辑、UI 交互设计、异常处理流程
- 总结章节（Summary）
  - 核心设计要点
  - 设计质量保证
  - 后续实施建议

**操作**: 使用 Edit 工具在文件末尾追加内容

#### 文件写入策略

1. **阶段 1 使用 Write**: 创建新文件，写入文档框架
2. **阶段 2-5 使用 Edit 追加**: 在文件末尾追加内容
3. **每个阶段独立完成**: 确认上一阶段写入成功后再进行下一阶段
4. **灵活分批**: 如果某个阶段内容过多，可以进一步细分为多次追加
5. **验证写入**: 每次写入后可以读取文件末尾部分验证是否成功

### 3. 架构边界原则（关键！）

**在设计过程中，必须遵循以下原则**:

1. **职责明确**:
   - 明确每个功能由 WMS 还是 WES 负责
   - 不要假设 WES 参与所有自动化流程
   - 当前阶段可能 WMS 独立完成某些功能

2. **API 设计**:
   - 只设计真正需要的 WMS-WES 集成 API
   - 不要设计 WMS 内部 API
   - 不要设计 WES 南向 API（设备接口）
   - 不要设计 WES 内部 API

3. **设备管理**:
   - 明确打印机由谁管理（WMS 直接 TCP？还是通过 WES？）
   - 明确 RCS 由谁调度（WMS 直接？还是通过 WES？）
   - 明确 PDA 连接到哪个系统

4. **数据归属**:
   - 明确哪些数据由 WMS 持有
   - 明确哪些数据由 WES 持有
   - 避免数据重复维护

5. **简化优先**:
   - 使用第一性原理思考
   - 避免过度设计
   - 能自动化的就自动化
   - 能简化的就简化

### 4. 输出格式

**文件名**: `docs/design/[章节号]-[功能名称].md`

例如: `docs/design/3.2.2-iqc-routing-review.md`

**语言**: 中文为主，技术术语保留英文，格式为"中文 (English)"

**Markdown 格式**:
- 使用标准 Markdown 语法
- 代码块使用 ```语言标识
- 表格使用标准 Markdown 表格
- Mermaid 图使用 ```mermaid

### 5. 迭代改进机制

如果用户指出架构边界错误（如"WES 不参与此阶段"），应该：
1. 立即更新相关章节
2. 移除不必要的 API 设计
3. 更新角色与归属表
4. 更新时序图
5. 更新代码示例
6. 确保文档内部一致性

**不要争辩，直接按用户指示修正**。

### 6. 设计审计

设计文档完成后，使用 `/audit-design` 命令进行审计：
```
/audit-design docs/design/[章节号]-[功能名称].md
```

审计将检查：
- 与 user_requirement.md 的需求覆盖率
- 内部一致性（角色、流程、时序、界面、数据）
- 架构合规性
- 可实施性

## 关键经验教训（从 3.2.1 设计中学到的）

### 架构边界教训

1. **不要假设 WES 参与所有流程**
   - 3.2.1 最终确认：WMS 全权负责码头收货绑定，WES 不参与
   - 教训：先明确职责边界，再设计流程

2. **不要假设需要 WMS-WES API**
   - 3.2.1 最终确认：无需任何 WMS-WES API
   - 教训：只设计真正需要的集成接口

3. **不要假设 WES 管理打印机**
   - 3.2.1 最终确认：WMS 通过 TCP 端口 9100 直接管理打印机
   - 教训：明确设备管理归属

4. **不要假设 WES 调度 RCS**
   - 3.2.1 最终确认：WMS 直接调度 RCS
   - 教训：明确硬件调度归属

### 业务逻辑教训

1. **箱数 ≠ 栈板数**
   - 不能从箱数自动推导栈板数
   - 需要人工根据实际情况确定

2. **一个箱子不可能需要多个栈板**
   - 但一个栈板可以装多个箱子

3. **使用第一性原理简化设计**
   - 去除不必要的确认页面
   - 自动化能自动化的步骤
   - 后台执行不阻塞用户

### 设计流程教训

1. **先读 SRS，再读 user_requirement**
2. **先明确架构边界，再设计流程**
3. **先设计核心流程，再设计 UI**
4. **先设计正常流程，再设计异常处理**
5. **持续审计，确保一致性**

## 关键经验教训（从 3.2.2 设计中学到的）

### 工作流模式教训

1. **不要假设自动推送 (Push) 总是最优**
   - 3.2.2 最初设计：自动触发送检，可能导致 IQC 待检区拥堵
   - 3.2.2 最终确认：采用拉动式 (Pull) 模式，IQC 人员根据工作负荷主动呼叫
   - 教训：考虑现场容量限制和人员控制需求，拉动式可能比推动式更有效

2. **不要假设自动完成总是可靠**
   - 3.2.2 最初设计：检验完成后自动触发路由
   - 3.2.2 最终确认：需要人工确认触发，确保样品归还和结果录入
   - 教训：关键节点需要人工确认，但要配合兜底机制（定时轮询）防止遗忘

3. **提醒机制 + 兜底机制 = 可靠性**
   - 高优先级提醒：优先级 ≥ 8 且等待 > 1小时
   - 长时间等待提醒：等待 > 4小时
   - 兜底机制：30分钟定时扫描，自动完成被遗忘的任务
   - 教训：设计要考虑人的遗忘，用技术手段保证流程不中断

### 业务实体关系教训

1. **一个栈板可能包含多个 GRN**
   - 3.2.2 最初设计：假设一个栈板对应一个 GRN
   - 3.2.2 实际情况：一个栈板可能有多个不同 GRN，处于不同检验状态
   - 教训：不要假设一对一关系，要考虑一对多、多对多的复杂关系

2. **一个 GRN 可能分布在多个栈板上**
   - 3.2.2 关键场景：GRN 检验 NG 时，需要移动所有包含该 GRN 的栈板
   - 3.2.2 设计方案：批量查询 + 批量生成搬运任务
   - 教训：业务实体的物理分布可能很复杂，要考虑批量操作

3. **管理对象选择：业务逻辑 > 物理操作**
   - 3.2.2 关键决策：以 GRN 还是栈板为主管理对象？
   - 3.2.2 最终确认：以 GRN 为主（QMS 策略、检验结果、优先级都针对 GRN）
   - 教训：选择管理对象时，优先考虑业务逻辑而非物理操作便利性

### 状态管理教训

1. **多状态实体需要状态筛选**
   - 3.2.2 场景：栈板上有多个 GRN，状态包括：未检、检验中、已完成、免检
   - 3.2.2 设计方案：只处理"检验中"状态的 GRN，其他状态不影响当前操作
   - 教训：处理多状态实体时，要明确筛选条件，避免误操作

2. **状态转换要考虑前置条件**
   - 3.2.2 场景：栈板上还有未检的 GRN 时，不能移动栈板
   - 3.2.2 设计方案：检查所有 GRN 状态，只有全部完成才移动栈板
   - 教训：状态转换前要检查所有相关实体的状态，不能只看当前操作的实体

3. **状态可视化很重要**
   - 3.2.2 设计增强：界面清晰区分"检验中 GRN"和"其他 GRN"
   - 3.2.2 设计增强：实时显示样品归还状态和 QMS 结果状态
   - 教训：复杂状态要可视化，让用户清楚知道当前状态和可执行操作

### 触发机制教训

1. **明确触发方式：自动 vs 人工**
   - 3.2.2 最初设计：触发方式不明确
   - 3.2.2 最终确认：送检呼叫（人工）、检验完成（人工+兜底）、复判完成（人工+兜底）
   - 教训：每个流程节点都要明确触发方式，不能含糊

2. **容量监控要实时可见**
   - 3.2.2 设计增强：实时显示 IQC 待检区容量（如：3/10）
   - 3.2.2 设计增强：选择栈板时动态显示容量变化
   - 教训：容量限制要可视化，帮助用户做决策

### 设计演进教训

1. **接受用户挑战，不要固守初始设计**
   - 用户质疑："自动触发有很大问题，是否由 IQC 人员自主选择会更有效？"
   - 设计响应：立即改为拉动式模式，重新设计整个流程
   - 教训：用户的现场经验往往比设计者的假设更准确

2. **通过提问发现隐藏需求**
   - 用户提问："如果该栈板中有多个不同的 GRN，该如何操作？"
   - 设计响应：发现多 GRN 栈板场景，重新设计状态管理
   - 教训：用户的"如果"问题往往揭示真实的复杂场景

3. **架构决策要基于业务本质**
   - 用户提问："IQC 待送检列表中应该是以栈板还是以 GRN 为主管理对象？"
   - 设计分析：QMS 策略针对 GRN、检验结果针对 GRN、优先级针对 GRN
   - 教训：架构决策要回归业务本质，不要被物理操作束缚

4. **设计要支持灵活性**
   - 3.2.2 设计方案：GRN 为主管理对象，但允许选择具体栈板
   - 3.2.2 设计方案：一个 GRN 可以分批送检（选择不同栈板）
   - 教训：设计要在业务逻辑和操作灵活性之间找到平衡

### 界面设计教训

1. **两步选择比一步选择更灵活**
   - 3.2.2 设计方案：先选择 GRN，再选择该 GRN 分布的栈板
   - 好处：用户可以根据容量、位置、数量灵活选择
   - 教训：不要过度简化界面，适当的步骤分解能提供更好的控制

2. **确认对话框要显示影响**
   - 3.2.2 设计增强：确认对话框显示"当前容量 3/10 → 5/10"
   - 3.2.2 设计增强：显示预计到达时间、优先级等关键信息
   - 教训：确认对话框不只是确认，要让用户看到操作的影响

3. **实时更新 > 手动刷新**
   - 3.2.2 技术选择：使用 SignalR 实现实时状态更新
   - 好处：样品归还、QMS 结果录入后，界面自动更新
   - 教训：关键状态变化要实时推送，不要让用户手动刷新

### 数据一致性教训

1. **批量操作要保证原子性**
   - 3.2.2 场景：一个 GRN NG 时，需要移动多个栈板
   - 3.2.2 设计考虑：批量生成搬运任务，要么全部成功，要么全部失败
   - 教训：批量操作要考虑事务性，避免部分成功部分失败

2. **跨系统数据要明确归属**
   - 3.2.2 明确：WMS 持有栈板、GRN、库存数据
   - 3.2.2 明确：QMS 持有抽样策略、检验结果数据
   - 教训：不要让两个系统都维护同一份数据，明确数据归属

### 设计流程教训（补充 3.2.1 的教训）

1. **先理解业务实体关系，再设计流程**
2. **先明确触发机制，再设计自动化**
3. **先设计状态管理，再设计状态转换**
4. **先考虑异常场景，再优化正常流程**
5. **持续接受用户反馈，迭代改进设计**
