# 设计文档生成器 (Design Document Generator)

基于 SRS 规格文档和具体需求章节，生成详细设计文档。

## 使用方法

```
/design <章节号> <章节名称>
```

**示例**:
```
/design 3.2.2 IQC 动态路由与复判
```

---

## 工具与思考模式 (Tools & Thinking Mode)

**启用模式**: `--ultrathink` (最大深度分析，~32K tokens)

**可用工具**:
- **Sequential Thinking** (`mcp__sequential-thinking__sequentialthinking`): 复杂推理、架构分析、假设验证
- **Serena Tools** (`mcp__serena__*`): 代码探索、符号操作、项目记忆管理
  - `search_for_pattern`, `list_dir`, `find_file` - 文档定位
  - `write_memory`, `read_memory` - 设计记忆持久化
- **Context7** (`mcp__context7__*`): 技术栈文档查询、框架最佳实践
  - `resolve-library-id`, `get-library-docs` - 官方文档查询
- **WebFetch** (`WebFetch`): 在线资源获取、技术文档补充

**使用场景**:
- 架构设计分析 → Sequential Thinking
- 文档模式搜索 → Serena search tools
- 技术栈文档 → Context7
- 在线资源补充 → WebFetch
- 设计记忆管理 → Serena memory tools

## 执行步骤

### 0. 交互式需求理解与确认（必须！）

**重要原则**: 不要假设，不要猜测，必须与用户充分沟通确认！

#### 0.1 初步需求理解

**询问用户**:
1. **功能范围确认**:
   - 这个功能的核心目标是什么？
   - 涉及哪些业务流程？（收货/入库/出库/盘点等）
   - 涉及哪些仓库区域？（码头/IQC/SMT/机构件等）

2. **系统职责边界**:
   - 这个功能主要由哪个系统负责？（WMS/WES/ECS）
   - WMS 和 WES 的职责分工是什么？
   - 是否需要 WMS-WES 集成？如果需要，集成点在哪里？

3. **硬件涉及情况**:
   - 是否涉及硬件设备？（AGV/机械臂/传感器/PDA/打印机等）
   - 硬件由谁管理？（WMS 直接管理 vs 通过 WES 管理）
   - 是否需要 RCS 调度？

**输出**: 明确的功能范围和系统职责边界

#### 0.2 物理布局调研（针对硬件密集型功能）

**适用场景**: 涉及硬件设备、传感器、机械臂、流水线等物理设备的功能

**询问用户**:
1. **物理布局**:
   - 物理硬件布局是什么？（流水线、工位、传感器位置）
   - 有多少工位？容量是多少？
   - 物理尺寸限制是什么？

2. **硬件自主控制**:
   - 硬件有哪些自主控制循环？（如：传感器触发 → 硬件动作）
   - 哪些操作由 ECS 自主完成？
   - 哪些操作需要 WES 协调？

3. **硬件职责边界**:
   - ECS 自主控制的范围是什么？
   - ECS 需要向 WES 上报哪些结果？
   - WES 需要向 ECS 下发哪些指令？

**输出**: 在设计文档中创建 §3.0 物理布局与硬件配置章节

#### 0.3 业务流程确认

**询问用户**:
1. **正常流程**:
   - 正常情况下的业务流程是什么？
   - 每个步骤的参与方是谁？（人工/WMS/WES/ECS/RCS）
   - 每个步骤的输入和输出是什么？

2. **异常流程**:
   - 可能出现哪些异常情况？
   - 异常情况如何处理？
   - 是否需要人工介入？

3. **数据流向**:
   - 数据从哪里来？（SAP/WMS/扫描/人工录入）
   - 数据到哪里去？（WMS/WES/SAP）
   - 数据在什么时候可用？

**输出**: 明确的业务流程和数据流向

#### 0.4 架构边界确认

**与用户确认**:
1. **WMS 职责**:
   - WMS 负责哪些功能？
   - WMS 是否提供人工兜底流程？
   - WMS 管理哪些数据？

2. **WES 职责**:
   - WES 负责哪些功能？
   - WES 是否参与这个流程？
   - WES 提供哪些自动化增强？

3. **ECS 职责**:
   - ECS 需要提供哪些能力？（能力需求，不是实现细节）
   - ECS 的接口规范是什么？（参考 whitepaper）

4. **集成接口**:
   - 是否需要 WMS-WES API？如果需要，具体是什么？
   - 是否需要 WES-ECS 接口？如果需要，具体是什么？
   - 是否需要其他集成？（SAP/QMS/SFC）

**输出**: 明确的架构边界和集成接口

#### 0.5 确认完成检查

**在开始生成设计文档之前，确认以下问题都已明确**:
- [ ] 功能范围和目标已明确
- [ ] 系统职责边界已明确（WMS/WES/ECS）
- [ ] 物理布局和硬件配置已明确（如涉及硬件）
- [ ] 业务流程和数据流向已明确
- [ ] 异常处理机制已明确
- [ ] 集成接口需求已明确
- [ ] 所有不确定的地方都已与用户确认

**如果有任何不确定的地方，必须先与用户确认，不要猜测！**

### 2. 生成设计文档（分阶段写入）

**重要**: 为避免 TOKEN 超长，设计文档必须分阶段生成和写入。

#### 阶段 1: 创建文档框架（Write 工具）

**包含内容**:
- 文档标题
- 技术栈说明 (Technology Stack)
  - WMS 技术架构（ASP.NET MVC WebForm 前后端不分离）
  - WES 技术架构（Python/FastAPI）
  - 集成架构图（Mermaid 格式）
  - ASP.NET MVC 代码示例（如有 WMS-WES 交互）
  - 配置说明（Web.config）
  - 部署架构图（Mermaid 格式）
- 范围与依据 (Scope & Traceability)
- 角色与归属 (Actors & Ownership)
- 前提与配置 (Preconditions & Config)

**操作**: 使用 Write 工具创建文件 `docs/design/[章节号]-[功能名称].md`

#### 阶段 2: 添加核心流程设计（Edit 工具追加）

**包含内容**:
- 子功能流程设计 (Sub-function Flows)
  - 按业务流程顺序，每个子功能包含：
    - 流程步骤（编号清晰）
    - 参与方（WMS/WES/RCS/人工/设备）
    - 数据流向
    - 校验逻辑
    - 异常处理

**操作**: 使用 Edit 工具在文件末尾追加内容

#### 阶段 3: 添加验收标准和测试场景（Edit 工具追加）

**包含内容**:
- 验收标准 (Acceptance Criteria)
  - 功能验收标准（核心功能、集成、数据一致性）
  - 性能验收标准（响应时间、吞吐量、并发）
  - 安全验收标准（认证、授权、加密、审计）
  - 可靠性验收标准（幂等性、错误恢复、回退机制）
- 测试场景 (Test Scenarios)
  - 正常流程测试（前置条件、测试步骤、预期结果、验证点）
  - 异常流程测试（触发条件、预期行为、错误恢复）
  - 边界条件测试（最小值、最大值、边界值）
  - 集成测试场景（涉及系统、验证点）
  - 性能测试场景（测试条件、性能指标）
  - 安全测试场景（测试步骤、预期结果）

**操作**: 使用 Edit 工具在文件末尾追加内容

#### 阶段 4: 添加时序图和对齐要点（Edit 工具追加）

**包含内容**:
- 典型时序 (Mermaid Sequence)
- 工业操作对齐要点 (Industrial Ops Alignment)
  - 顺序控制、区域一致性、安全约束、幂等与恢复、边界遵循
- 数据要点 (Data Notes)
  - 关键数据对象、数据归属（WMS/WES）、数据结构示例

**操作**: 使用 Edit 工具在文件末尾追加内容

#### 阶段 5: 添加数据库模型和数据字典（Edit 工具追加）

**包含内容**:
- 数据库模型 (Database Schema)
  - 表定义（字段、类型、约束、索引、关系）
- 数据字典 (Data Dictionary)
  - 业务对象数据字典（数据项定义、业务规则、数据来源、数据流向、关联对象）
  - 枚举类型数据字典（枚举值定义、使用场景）
  - 接口数据字典（接口路径、认证、限流、请求参数、成功响应、错误响应、业务规则、请求示例、响应示例）

**操作**: 使用 Edit 工具在文件末尾追加内容

**注意**: 如果内容过多（>5个业务对象或>5个接口），可以分批追加

#### 阶段 6: 添加性能、安全和错误处理规范（Edit 工具追加）

**包含内容**:
- 性能要求 (Performance Requirements)
  - 响应时间要求（API、页面、PDA）
  - 吞吐量要求（TPS、并发用户、数据处理能力）
  - 资源使用要求（CPU、内存、数据库连接池）
  - 可扩展性要求（水平扩展、数据库扩展、缓存策略）
  - 性能监控指标
- 安全要求 (Security Requirements)
  - 认证机制（WMS、WES、外部系统）
  - 授权控制（角色定义、权限控制、权限验证）
  - 数据保护（传输加密、存储加密、数据脱敏）
  - 审计日志（审计范围、审计内容、审计日志存储）
  - 安全防护（输入验证、访问控制、安全配置）
- 错误处理规范 (Error Handling)
  - 错误码定义（WMS、WES、集成错误码）
  - 错误响应格式（标准错误响应、字段说明）
  - 异常处理策略（重试策略、降级策略、补偿机制）
  - 错误日志记录（日志级别、日志内容）

**操作**: 使用 Edit 工具在文件末尾追加内容

#### 阶段 7: 添加功能页面设计（Edit 工具追加）

**包含内容**:
- 功能页面设计 (Functional Page Design)
  - WMS Web 页面（路径、角色、页面元素、交互逻辑、关键特性）
  - WMS PDA 界面（界面类型、角色、界面流程、界面特性）

**操作**: 使用 Edit 工具在文件末尾追加内容

#### 阶段 8: 添加监控、部署和可访问性（Edit 工具追加）

**包含内容**:
- 监控与日志 (Monitoring & Logging)
  - 监控指标（系统、应用、业务、硬件）
  - 日志规范（日志级别、日志内容、日志格式、日志存储）

  - 部署流程（部署前检查、部署步骤、部署策略）

  - WCAG 合规性（合规级别、关键要求）
  - 键盘访问（键盘导航、快捷键）

#### 阶段 10: 添加团队分工（Edit 工具追加）

**包含内容**:
- 团队分工表 (Team Responsibilities)
  - 明确 WMS、WES、ECS 三个团队的职责边界
  - 每个功能点的实施团队
  - 跨团队协作接口

**表格格式**:
| 功能点 | 功能简述 | 团队分工 | 备注 |
|--------|----------|----------|------|
| [功能名称] | [简要描述] | WMS/WES/ECS/协同 | [特殊说明] |

**团队说明**:
- **WMS 团队**: .NET Framework + ASP.NET MVC + SQL Server - 负责业务逻辑、Web 界面、PDA 界面、SAP 集成（系统升级项目，人工兜底）
- **WES 团队**: Python + FastAPI + SQLModel + PostgreSQL + Redis - 负责调度引擎、策略执行、硬件协调、状态管理（全新开发项目，自动化增强）
- **ECS 团队**: 外部硬件供应商 - 按照 `third_party_integration_whitepaper.md` 提供设备能力接口
- **协同**: 需要多团队配合完成的功能

**项目性质说明**:
- **WMS**: 系统升级项目，需考虑现有系统兼容性、数据迁移、业务连续性
- **WES**: 全新开发项目，可采用现代架构和最佳实践，无历史包袱

**职责分工说明**:
- **WMS 负责人工兜底**: 提供完整的人工操作流程，确保业务连续性，是业务的安全网
- **WES 负责自动化增强**: 在 WMS 基础上增加自动化能力，提升效率，是效率的加速器
- **回退机制**: 自动化失败时，必须能回退到 WMS 的人工流程

**外部团队说明**:
- ECS 是外部硬件供应商，设计文档只定义能力需求和接口规范
- 不描述 ECS 内部实现细节（如传感器类型、PLC 逻辑、控制算法）
- 所有 WES-ECS 交互遵循 `docs/third_party_integration_whitepaper.md` 定义的接口规范

**操作**: 使用 Edit 工具在文件末尾追加内容

### 3. 架构边界原则（关键！）

**在设计过程中，必须遵循以下原则**:

1. **职责明确**:
   - 明确每个功能由 WMS 还是 WES 负责
   - 不要假设 WES 参与所有自动化流程
   - 当前阶段可能 WMS 独立完成某些功能

2. **API 设计**:
   - 只设计真正需要的 WMS-WES 集成 API
   - 不要设计 WMS 内部 API
   - 不要设计 WES 南向 API（设备接口）
   - 不要设计 WES 内部 API

3. **设备管理**:
   - 明确打印机由谁管理（WMS 直接 TCP？还是通过 WES？）
   - 明确 RCS 由谁调度（WMS 直接？还是通过 WES？）
   - 明确 PDA 连接到哪个系统

4. **数据归属**:
   - 明确哪些数据由 WMS 持有
   - 明确哪些数据由 WES 持有
   - 避免数据重复维护

5. **简化优先**:
   - 使用第一性原理思考
   - 避免过度设计
   - 能自动化的就自动化
   - 能简化的就简化

6. **外部硬件供应商边界**:
   - 硬件供应商（ECS）是外部团队，不描述其内部实现细节
   - 只定义能力需求和接口规范（WHAT），不描述实现方法（HOW）
   - 所有硬件交互必须遵循 `docs/third_party_integration_whitepaper.md`
   - 使用"需要提供...能力"而非"使用...技术实现"
   - 物理布局和约束可以描述（影响业务逻辑），但控制逻辑不描述

7. **WMS/WES 职责分工**:
   - **WMS 负责人工兜底**：提供完整的人工操作流程，确保业务连续性
   - **WES 负责自动化增强**：在 WMS 基础上增加自动化能力，提升效率
   - WMS 是业务的安全网，WES 是效率的加速器
   - 自动化失败时，必须能回退到 WMS 的人工流程
   - 设计时优先保证 WMS 人工流程完整，再考虑 WES 自动化增强

### 4. 输出格式

**文件名**: `docs/design/[章节号]-[功能名称].md`

例如: `docs/design/3.2.2-iqc-routing-review.md`

**语言**: 中文为主，技术术语保留英文，格式为"中文 (English)"

**Markdown 格式**:
- 使用标准 Markdown 语法
- 代码块使用 ```语言标识
- 表格使用标准 Markdown 表格
- Mermaid 图使用 ```mermaid

### 5. 迭代改进机制

如果用户指出架构边界错误（如"WES 不参与此阶段"），应该：
1. 立即更新相关章节
2. 移除不必要的 API 设计
3. 更新角色与归属表
4. 更新时序图
5. 更新代码示例
6. 确保文档内部一致性

**不要争辩，直接按用户指示修正**。

### 6. 设计审计

设计文档完成后，使用 `/audit-design` 命令进行审计：
```
/audit-design docs/design/[章节号]-[功能名称].md
```

审计将检查：
- 与 user_requirement.md 的需求覆盖率
- 内部一致性（角色、流程、时序、界面、数据）
- 架构合规性
- 可实施性
